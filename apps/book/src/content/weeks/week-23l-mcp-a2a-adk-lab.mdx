<Hook>Two agents can exchange valid messages and still do the wrong job at twice the price. What contract is missing?</Hook>

<Intuition>
Imagine a research office with a shared catalogue, a colleague at another desk, and a workflow application. A catalogue request needs a tool interface. Delegating a report needs a task identity and lifecycle. The application decides when to call either one. None of those interfaces tells you whether the finished report is correct or worth its cost.

These roles map roughly to **MCP**, **A2A** and an agent framework such as **ADK**. MCP originated at **Anthropic**. A2A and ADK are **Google Cloud** initiatives, not Google DeepMind products. Do not merge a company's model research, application SDKs and communication standards into one attribution or one trust boundary.

<IntuitionCallout>Make four moves: define the message contract; bind execution to a principal and budget; verify resulting artifacts independently; account for every token and retry. Interoperability, safety, correctness and economics are different properties.</IntuitionCallout>

The reference makes these boundaries executable. A local MCP JSON-RPC server/client exchanges serialized messages for initialization, tool listing and tool calls. A separate A2A-shaped demo tracks submitted, working and terminal tasks. Two tiny repository-shaped tasks exercise an evaluation harness. Routing and response caching remain independent of the protocol. Real Google Cloud ADK construction is available behind a lazy optional import, never required for the offline exercises.

**Scope matters:** the MCP code is a reduced teaching subset referencing version **2024-11-05**; the A2A demo is **local teaching subset v0.1**, not wire-compliant A2A. No real SWE-Bench evaluation or cloud model execution is smuggled into a fixture result.

## The math, derived

### 1. Partition the bill before optimizing it

Let I be total input tokens, H cached-read input tokens, W cache-write input tokens, and O output tokens. These are disjoint input categories in this teaching ledger, so fresh input is I − H − W. Let pᵢ, pₕ, p𝓌 and pₒ be dollars per million tokens, with p𝓌 an **all-in write price**, not a surcharge. Then:

<MathBlock latex="C=\frac{(I-H-W)p_i+Hp_h+Wp_w+Op_o}{10^6},\qquad H+W\le I" />

Worked example: I = 1,000, H = 400, W = 200, O = 100. Hypothetical prices are $2 fresh, $.50 cached read, $2.50 cache write and $8 output per million. Fresh input is 400 tokens:

<MathBlock latex="C=\frac{400(2)+400(0.5)+200(2.5)+100(8)}{10^6}=\$0.0023" />

A hypothetical uniform batch multiplier of .5 gives $0.00115. This is **not a provider price quote** or a promise that batch and cache discounts stack uniformly. Production accounting must pin a dated rate card, tokenizer, regional/model version, cache eligibility, write-price convention and failed/retried request billing. Batch processing can lower unit price while increasing queueing latency; an interactive agent may not be eligible.

### 2. Cache reuse has a break-even point

Consider an unchanged P-token prefix used n times. Let a be the all-in price per token for the initial cache write, b the cached read price and c the ordinary input price. Ignoring expiration and storage fees, caching is cheaper when:

<MathBlock latex="Pa+(n-1)Pb<nPc\quad\Longleftrightarrow\quad n>\frac{a-b}{c-b},\qquad c>b" />

With a = 2.5, b = .5 and c = 2 in consistent per-million units, n > 2/1.5 = 4/3. Thus **two uses** suffice under those assumptions. For a 1,000-token prefix, two fresh reads cost $.004; write plus one cached read costs $.003. A miss, expiry or changed prefix may eliminate that saving.

Provider **prompt/prefix caching** reuses computation for a matching context prefix. Our **response cache** returns a previously computed answer without invoking a model. They have different semantics. Response reuse must bind authenticated principal scope, model, prompt, context/tool revisions and decoding parameters. Do not return a stale answer because only the literal prompt matched.

### 3. Route under constraints, not by price alone

For each candidate model j, estimate cost Cⱼ, quality qⱼ and latency ℓⱼ from appropriately held-out evidence. Choose the cheapest eligible route:

<MathBlock latex="j^*=\arg\min_j C_j\quad\text{subject to}\quad q_j\ge q_{\min},\;\ell_j\le L_{\max},\;C_j\le C_{\max}" />

Suppose a small route costs $.001, scores .70 and takes 60 ms; a larger route costs $.003, scores .90 and takes 150 ms. A .80 quality floor and 200 ms limit admit only the larger route. Tightening the latency limit to 100 ms admits neither. The correct response is an explicit no-route/fallback decision, not silently lowering the quality bar.

The code accepts fixture quality/latency values; it does not predict request difficulty or estimate real service latency. In deployment, route on observable task features and validate by task slice, with uncertainty and distribution-shift monitoring. Distillation can reduce serving cost but adds teacher/data/training expense and may lose tail capabilities. Amortize that work over expected volume rather than treating a smaller model as free.

### 4. Retry changes cost and the evaluation denominator

With independent per-attempt success probability p, at most K attempts, and constant attempt cost c, the probability of at least one success and expected number of attempts are:

<MathBlock latex="P(\mathrm{success})=1-(1-p)^K,\qquad \mathbb E[N]=\sum_{k=1}^{K}(1-p)^{k-1}=\frac{1-(1-p)^K}{p}" />

At p = .5 and K = 3, success is .875 and expected attempts are 1 + .5 + .25 = 1.75. At $.002 per attempt, expected cost is $.0035. Repeated model attempts often have correlated failures and expanding context, so this is a baseline model, not an empirical guarantee. A cost-per-success metric should include failures in its total-spend numerator, not just the successful traces.

For N frozen tasks, let tᵢ indicate independently verified task success and bᵢ any denied attempt. Missing submissions are failures rather than removed rows:

<MathBlock latex="\mathrm{task\ success}=\frac1N\sum_i t_i,\qquad \mathrm{safe\ success}=\frac1N\sum_i t_i(1-b_i),\qquad \mathrm{cost/success}=\frac{\sum_i C_i}{\sum_i t_i}" />

When no task succeeds, cost per success is undefined, not zero. In our two-task fixture, both patches can pass while one trajectory has a denied attempt: task success = 1.0, safe success = .5. That tiny development set tests harness mechanics; it cannot establish production reliability or a statistically meaningful model ranking.

## The code, from scratch

```python
from protocol_lab import LocalTransport, MCPClient, MCPServer

transport = LocalTransport(MCPServer(max_calls=4))
client = MCPClient(transport)
client.initialize()  # request/response, then initialized notification
assert [tool['name'] for tool in client.list_tools()] == ['add', 'lookup']
result = client.call_tool('add', {'a': 2, 'b': 3})
assert result == {'content': [{'type': 'text', 'text': '5'}], 'isError': False}
```

`LocalTransport` carries JSON strings, not shared Python objects. The same server runs over newline-delimited stdin/stdout using `python -m protocol_lab`; stream tests use StringIO rather than subprocesses or sockets. Requests have correlated IDs. Notifications produce no response. Each frame is bounded, and clients reject malformed envelopes, mismatched IDs, contradictory result/error bodies and malformed tool content.

### MCP lifecycle and error contracts

The local sequence is **initialize → initialized notification → tools/list or tools/call**. The pinned reference is MCP 2024-11-05, but this server deliberately omits resources, prompts, sampling, HTTP transport, auth, cancellation, pagination and complete schema semantics. It only implements the advertised primitive object schemas and text results. Unsupported versions are rejected rather than negotiated. Those reductions are why we call it a teaching subset, not compliant MCP.

| Boundary | Local behavior |
| --- | --- |
| Malformed JSON or oversized frame | JSON-RPC parse error `-32700` |
| Invalid request envelope | `-32600` |
| Unknown method | `-32601` |
| Invalid arguments, unknown tool, unsupported version | `-32602` |
| Tool request before initialization completes | local error `-32002` |
| Missing public record | normal RPC result with `isError: true` |
| Exhausted host call budget | local error `-32000` |

An execution failure is different from an invalid request. That distinction lets a controller recover appropriately without parsing error prose. Every admitted attempted tool call consumes the host budget, including invalid tool names or arguments. The only tools are bounded addition and a public in-memory catalogue: no arbitrary shell, file access or network tool exists.

### A2A task handoffs are not tool calls with a different name

A delegated task can outlive one request. The local demo carries a stable task ID, message, status and artifacts. It follows submitted → working → completed/failed, with cancellation permitted before a terminal state. Replaying the same ID and message is idempotent; changing the message under an existing ID is a conflict. Terminal tasks cannot silently restart.

The public-guide worker is a deterministic fixture, not a language model. The explicit `demo/advance` scheduler method is **not an A2A standard method**. The demo claims only local teaching subset v0.1; it does not implement a released A2A wire version, authenticated discovery, complete Agent Cards, streaming, push notification or remote delegation. Production handoffs need authenticated principals, cancellation semantics, deadlines, version negotiation and artifact provenance.

### Genuine optional ADK, without a hidden cloud dependency

The optional `protocol_lab.adk_sample` lazily imports `google.adk.agents.Agent`. Its typed `lookup_public_record` function becomes an actual ADK function tool. The optional run path uses the real `InMemoryRunner`, session service, `google.genai.types.Content` and `RunConfig(max_llm_calls=2)` APIs. This is SDK wiring, not a class with an ADK-like name.

The extra pins `google-adk==1.18.0` and belongs in a separate disposable environment. The default path constructs an agent only; model execution requires explicit `--run-model`, an available model ID, credentials and quota setup. The offline suite mocks the imported module and never installs or invokes the cloud SDK. Therefore **cloud/API compatibility was not validated by these tests**. A best-effort coroutine deadline does not guarantee provider-side cancellation or zero billing.

### Frameworks: choose state semantics before a logo

| Framework | Conceptual affordance to investigate in its pinned docs | Question before adoption |
| --- | --- | --- |
| LangGraph | Explicit state graphs, checkpointing and controlled transitions | Can a replay duplicate a consequential action? |
| CrewAI | Role/task-oriented crews and flows | Are task outputs independently checked or merely accepted by another role? |
| AutoGen | Agent conversations, message passing and team orchestration | Who owns termination, shared state and the global budget? |
| OpenAI Agents SDK | Agents, tools, handoffs, guardrails and tracing | Where is authorization enforced outside model instructions? |
| Google Cloud ADK | Agent composition, tools, sessions, runners and evaluation tooling | Which session/tool state is durable, isolated and versioned? |

This is a conceptual comparison, not a claim of feature parity, current-version guarantees or included framework implementations. The package does not counterfeit any of these libraries. A framework reduces application wiring; it does not remove the need to understand retries, resource bounds, data provenance or trust boundaries. Prefer a fixed workflow when it meets the product need with fewer failure modes.

### Knowledge-Graph RAG and context engineering

A knowledge graph stores entities and relations; retrieval can traverse relationships before selecting grounded text. In a public repository assistant, a graph might connect a symbol to its module, owner and documentation section. Retrieve candidate nodes, traverse a bounded number of typed edges, rerank source passages and cite the underlying file/version—not just an unsupported graph edge. Entity resolution errors and stale edges can confidently lead to the wrong source.

Graph structure is not a license to include the entire repository in context. Select a token budget across instructions, trusted task state, retrieved evidence and tool results. Preserve source IDs, freshness, unresolved subgoals and constraints. Separate instructions from quoted untrusted material; an instruction inside a retrieved README remains data. Compare graph-assisted retrieval against a simpler text/hybrid baseline using held-out queries, citation correctness and cost. Week 17 provides retrieval foundations; this protocol package does not implement another GraphRAG engine.

Prompt engineering shapes individual requests. Context engineering also determines **which state reaches the model, from where, at what version, and under which permissions**. Summaries, retrieval, tool schemas and caches all change that state. Test stale documents, conflicting sources, malicious-looking quoted instructions and missing evidence before celebrating a longer context window.

### Agent evaluation: artifacts and trajectories

The local evaluation harness edits only allowlisted existing files in in-memory mini repositories. It verifies a JSON timeout and README/package-version consistency independently of the supplied answer. Unknown/duplicate task IDs are errors; missing attempts stay in the denominator; path escapes, oversized replacements and budget excess fail. No patch is executed as Python or a shell command.

SWE-Bench evaluates repository issue resolution; **SWE-Bench Verified** is a curated real benchmark subset, not our two generated tasks. A real run needs official task/version data, reproducible repository environments, an isolated test harness and contamination controls. Report exact versions, environment failures and unresolved cases. Never label our classroom success fraction a SWE-Bench score.

**Inspect AI**, from the UK AI Security Institute, is an evaluation framework with real task, solver and scorer abstractions; it is not an Anthropic product merely because it can evaluate Claude. We discuss how an adapter could connect trusted trajectory logs and artifact verifiers, but do not ship a pretend Inspect integration. Extend [Week 20's evaluation discipline](/weeks/week-20-evals-mlops-pipeline): freeze task splits, calibrate any model judge against independent labels, log scorer versions, and report uncertainty and failure slices.

Trajectory metrics include attempts, denied calls, retries, completion status, wall time, tokens and cost. The reference implements the subset of counters available from deterministic local attempts, not measured cloud latency. In production, record counters at the trusted host—not from model-written statements about how many calls it made. Cost optimization cannot be evaluated honestly when unsuccessful traces disappear from the ledger.

<KeyTakeaways>
- MCP, A2A and ADK occupy different interface layers; correct attribution and version scope matter.
- Real serialized local execution can be useful without claiming full protocol conformance.
- Independently verify artifacts, preserve failed/denied trajectories and name the actual evaluation suite.
- Token partitions, cache semantics and retry denominators determine whether savings are real.
- Framework adoption and interoperability never replace host authorization, held-out evidence or explicit budgets.
