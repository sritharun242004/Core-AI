<Hook>A language model cannot learn from words until you decide what a token is, where a position lives, and what it means to predict the next symbol.</Hook>

<Intuition>
Tokenization is the interface between a byte string and a tensor. Characters waste sequence length; whole words cannot handle names, code, or new morphology. Byte-pair encoding starts small, counts adjacent pairs, and repeatedly merges the most useful pair. The resulting vocabulary is a compromise between sequence length, coverage, and the cost of the embedding and output matrices.

<IntuitionCallout>
A checkpoint is not just weights. It is weights plus configuration plus tokenizer vocabulary and merge rules. Change the tokenizer while keeping the tensor shapes and you have changed the model's language.
</IntuitionCallout>

The four moves are: train and round-trip a deterministic BPE vocabulary, derive the next-token objective, compare RoPE with ALiBi, and distinguish pretraining from every later post-training stage.

## The math, derived

### 1. BPE changes sequence length

Let a token sequence be $s=(s_1,\ldots,s_T)$. A merge replaces adjacent $(a,b)$ with a new symbol $ab$. The merge is selected by frequency:

<MathBlock latex="(a^*,b^*)=\arg\max_{(a,b)}\operatorname{count}(a,b)" />

The project uses a lexicographic tie-break, so the merge list is reproducible. Encoding applies the learned list in rank order; decoding expands each learned symbol back to its children. In production byte-level implementations, the initial alphabet and whitespace policy are more elaborate, but the contract is the same.

### 2. Next-token prediction

Given token IDs $x_1,\ldots,x_T$, a decoder predicts $x_{t+1}$ from the prefix $x_{\le t}$. For logits $z_t$ and target $x_{t+1}$:

<MathBlock latex="p_\theta(x_{t+1}\mid x_{\le t})=\operatorname{softmax}(z_t)_{x_{t+1}},\qquad L(\theta)=-\frac{1}{T-1}\sum_{t=1}^{T-1}\log p_\theta(x_{t+1}\mid x_{\le t})" />

The training implementation shifts each window by one and applies cross-entropy over every next-token position. Pretraining learns broad continuation behavior from the token stream; supervised fine-tuning and preference optimization are later objectives, not alternative names for the same phase.

### 3. RoPE: relative phase through absolute rotations

For a query/key pair $(q_{2i},q_{2i+1})$, position $p$ applies a 2D rotation with angle $p\omega_i$:

<MathBlock latex="R(\theta)=\begin{bmatrix}\cos\theta&-\sin\theta\\\sin\theta&\cos\theta\end{bmatrix},\qquad q'_p=R(p\omega_i)q_p" />

Because both query and key are rotated before their dot product, their interaction depends on a relative phase between positions. The frequency schedule uses different angular rates for different feature pairs. It is a geometric transformation, not an extra learned token ID.

### 4. ALiBi and long context

ALiBi keeps content vectors unchanged and adds a head-specific distance penalty to attention scores:

<MathBlock latex="s_{h,i,j}=\frac{q_{h,i}^\top k_{h,j}}{\sqrt{d_h}}-m_h(i-j),\qquad i\ge j" />

Some heads receive a steep slope and focus locally; others receive a shallow slope. YaRN and other long-context methods modify or extend positional behavior, but the engineering test remains the same: evaluate retrieval and perplexity at longer lengths without confusing one synthetic needle test for general reasoning.

<Gotcha>Never load a checkpoint with a different vocabulary and call the failure a “position issue.” Token IDs, merge ranks, embedding rows, output rows, sequence length, and positional configuration all belong in the compatibility contract.</Gotcha>

<KeyTakeaways>
- Tokenizer merges, special IDs, and normalization rules are part of the model interface.
- Causal pretraining is next-token prediction over a one-position-shifted stream.
- RoPE rotates query/key pairs; ALiBi adds distance-dependent score biases.
- Pretraining, supervised fine-tuning, and preference optimization answer different objectives.
- A long-context plot is only as trustworthy as its tokenizer, split, metric, and evaluation task.
</KeyTakeaways>
