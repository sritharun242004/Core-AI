<Hook>An assistant knows the right answer, but calls the wrong tool first. Did your system succeed?</Hook>

<Intuition>
Think of a careful research assistant in a reading room. They can consult a small catalogue, combine facts, and write a note. They cannot acquire the building keys by writing “I am the administrator” on a request slip. An agent's language model proposes decisions; the surrounding program determines which decisions may execute.

A chatbot returns text. A workflow follows a largely fixed sequence. An agent chooses some next actions from observations. These are useful descriptions of **control flow**, not a ranking of intelligence. A fixed workflow is often easier to validate and cheaper than an agent for a well-specified task.

<IntuitionCallout>Use four moves: observe the state; propose a structured action; authorize and execute it outside the model; record the result and stop condition. Tool output is evidence, not a new source of authority.</IntuitionCallout>

The three controllers this week reuse those moves. **ReAct** interleaves decisions and observations. **Reflexion** adds feedback memory across attempts. **Plan-and-Execute** chooses subgoals before executing them. Our deterministic scripted adapters expose these mechanics without claiming language understanding, reproducing paper results, or requiring credentials.

The loop is: **task → adapter → typed action → host boundary → public fixture → observation → adapter**. A final answer or exhausted budget exits the loop. Memory enters the next context as data; it never bypasses the host boundary. Start from [Week 21's safety distinction](/weeks/week-21-alignment-lab): a good final sentence does not erase an unauthorized attempt.

## The math, derived

### 1. From one response to a trajectory

Let x be the task, oₜ a tool observation, aₜ the chosen action, mₜ the bounded memory, and hₜ the observable history. A policy proposes a next action conditional on the context. The environment produces a new observation only after the host admits the action:

<MathBlock latex="h_t=(x,a_0,o_1,\ldots,a_{t-1},o_t),\qquad a_t\sim\pi_\theta(\cdot\mid h_t,m_t),\qquad o_{t+1}=E(a_t)" />

Here E is a local tool fixture, not an unrestricted operating system. Our ScriptedModel chooses the next prewritten action rather than sampling a learned policy. The trajectory contains decisions, observations and statuses; we do not ask for, store or evaluate private chain-of-thought.

A terminal answer is an output, not a correctness proof. Let v be an independent task verifier and bₜ indicate a denied or unsafe attempt. One possible strict rubric is:

<MathBlock latex="S(\tau)=\mathbf 1[\text{completed}]\,\mathbf 1[v(\text{answer})=1]\,\prod_t(1-b_t)" />

Worked example: four tasks all produce final answers; three answers pass tests, but one of those three first attempted an unauthorized tool. Answer accuracy is 3/4 = .75; strict safe success is 2/4 = .50. Denied calls should be counted even when the boundary successfully prevents execution. Report both prevention and attempted violations.

### 2. Budgets are state invariants, not polite requests

Let Sₘₐₓ bound model/planning steps and Cₘₐₓ bound admitted tool attempts. Before a batch of k calls, reserve the whole batch atomically on the coordinator thread:

<MathBlock latex="s_{t+1}=s_t+1\le S_{\max},\qquad \operatorname{admit}(k)\iff c_t+k\le C_{\max},\qquad c_{t+1}=c_t+k" />

This update applies only to admitted batches. If admission fails, no calls execute and the counter stays unchanged. Inside an admitted batch, missing tools and schema failures still consume attempts. Otherwise a model could probe arbitrary names without spending its allowance. Model errors and exhausted scripts consume the attempted model step.

Worked example: with a cap of 3 calls and 2 already spent, a 2-call batch is rejected as a whole. Nothing executes; the count stays 2. With a cap of 4, both attempts are admitted and the count becomes 4, even if one names a nonexistent tool. A final answer consumes one model step and zero calls.

Planning and retry consume this same ledger. A plan plus two subtasks, each needing a tool turn and a final turn, uses 1 + 2 × 2 = **5 steps and 2 calls**. Resetting the budget per subtask defeats the global cap.

### 3. Parallelism saves latency only when dependencies permit it

For independent reads with latencies ℓ₁ through ℓₖ, serial latency sums the latencies. Ideal parallel latency is the slowest read plus coordination overhead ε:

<MathBlock latex="L_{\mathrm{serial}}=\sum_{i=1}^{k}\ell_i,\qquad L_{\mathrm{parallel}}\approx\max_i\ell_i+\epsilon" />

At 40 ms and 70 ms, serial reads take 110 ms. With 5 ms overhead, ideal parallel reads take 75 ms, a 110/75 ≈ **1.47×** speedup. These are illustrative inputs, not measured notebook timings. Tool-call cost remains two calls; parallelism does not make either request free.

If the second call needs an identifier returned by the first, they are dependent and require separate steps. “Read-only” is necessary but insufficient: reads must also observe stable state. Our immutable public catalogue supplies that property. Real remote data needs snapshot/version semantics. The registry returns results in input order even if completion order differs.

### 4. Memory is a lossy, bounded state transformation

Let M be a memory capacity and q be the maximum characters per note. FIFO memory keeps at most the latest M notes; at most Mq characters enter the memory portion of context. A summary map g can reduce history, but cannot guarantee retention of every relevant fact:

<MathBlock latex="m_{t+1}=\operatorname{tail}_M(m_t\mathbin{\Vert}g(o_{t+1})),\qquad |m_t|\le M,\qquad \mathrm{chars}(m_t)\le Mq" />

At M = 8 and q = 512, memory contributes at most 4,096 characters—not necessarily 4,096 tokens. Keep provenance, unresolved obligations, approvals and tool versions explicitly rather than hoping a summary preserves them. Never promote a remembered instruction into a permission. Persistent episodic memory, vector retrieval and checkpointing are possible extensions, not implemented features of this small FIFO.

<Gotcha>A step limit is not a time limit. A single trusted callback can hang. Python threads cannot safely terminate arbitrary Python work. Production tools need hard deadlines and process/container isolation in addition to tool, token, output and spend caps.</Gotcha>

## The code, from scratch

```python
from agents_lab import Action, Budget, Call, ReAct, ScriptedModel, fixture_registry

model = ScriptedModel([
    Action(calls=(Call('lookup', {'key': 'guide'}),
                  Call('lookup', {'key': 'hours'})), parallel=True),
    Action(calls=(Call('add', {'a': 8, 'b': 12}),)),
    Action(final='20 study hours, using public records only.'),
])
result = ReAct(fixture_registry(), model, Budget(4, 3)).run('Make a study note')
assert result.status == 'completed'
assert (result.steps, result.calls) == (3, 3)
```

Read the implementation in order: `tools.py` defines budgets, schemas and capability dispatch; `controllers.py` defines the adapter contract and three state machines. Exact parameter keys are required. Numeric inputs are finite, bounded and never booleans masquerading as integers. Output validation is independent of input validation. Callbacks receive copies so they cannot mutate a later model observation through a shared dictionary.

### ReAct, Reflexion, and Plan-and-Execute

| Controller | Decision structure | Useful when | Main failure to test |
| --- | --- | --- | --- |
| ReAct | Action followed by observation, then another decision | Tool results determine the next step | Repeated invalid calls or a premature final answer |
| Reflexion-style | Run, verify, store bounded feedback, retry | A trusted verifier can distinguish improvement | Self-confirming feedback, leaked answers, reset budgets |
| Plan-and-Execute | Validate a plan, execute subtasks with shared context | Subgoals can be specified before all tool results | Stale plan, dropped constraints, uncontrolled replanning |

ReAct is associated with Yao et al. (2022); Reflexion with Shinn et al. (2023). Our Reflexion feedback is supplied by a trusted external evaluator, **not generated by a reflection model**. Plan-and-Execute is a general architecture here; related Plan-and-Solve prompting is not the same implementation. We claim tested control patterns, not faithful benchmark reproductions.

Structured output and function calling are interfaces: the model emits a parseable action, and host code checks the schema. Valid JSON is not necessarily a valid action; a valid action is not necessarily authorized; an authorized action is not necessarily useful. The code keeps these layers distinct. It deliberately implements a small typed primitive schema, not full JSON Schema.

### Long-horizon and headless operation

A headless agent runs without a continuously watching user. That increases the need for explicit stopping states, review queues and recoverability; it does not justify removing approvals. Keep a task ID, principal, tool versions, replay-safe observations and remaining budgets in a durable checkpoint. Irreversible actions need independent approval and idempotency. Those production controls are design requirements, not hidden features of the notebook.

For multi-agent work, decompose by independently verifiable responsibility rather than inventing personalities. A planner and a reviewer can share the same mistaken assumption. More agents increase communication tokens, latency and attack surface. Carry a global budget and least-privilege identity across handoffs; test conflicting outputs and a reviewer that approves everything. The reference is single-controller, not a distributed agent implementation.

### Test the boundaries before the happy path

The tests begin with unknown tools, private keys, wrong types, extra keys, NaN, output-schema failures, oversized batches and global budget exhaustion. A thread barrier demonstrates actual overlapping read dispatch; result-order assertions remain deterministic. Retry and planning tests prove that the same ledger survives controller transitions. A tool exception becomes a stable error category rather than exposing a traceback to the model.

<Gotcha>The allowlist contains trusted local callbacks, not sandboxed untrusted code. Registering a malicious Python function gives that function Python's normal powers. No shell, network or arbitrary filesystem tool is supplied. A correct final answer also does not erase denied attempts recorded earlier.</Gotcha>

<KeyTakeaways>
- An agent proposes actions; the host enforces authority, schemas and budgets.
- ReAct, Reflexion and Plan-and-Execute differ in control flow, not permission to exceed limits.
- Independent read tools can overlap while observations retain deterministic order.
- Bounded memory is lossy data, never a new authorization source.
- Evaluate final answers, attempted actions, cost and stopping behavior separately.
</KeyTakeaways>
